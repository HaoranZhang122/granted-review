Three native queries use MySQL-only syntax and fail on PostgreSQL

Three of the 43 native SQL queries stop with a syntax error on PostgreSQL. Rewrite them, with a per-database version where no common form exists.

Show details

The problem

The order service has 43 native SQL queries. The ORM does not write them, so they do not change with the database. Three of them use syntax that only MySQL accepts.

What we found

  • [READ] A search of the code found 3 MySQL-only forms: ON DUPLICATE KEY UPDATE, GROUP_CONCAT and LIMIT 40, 20. [report.md]
  • [TESTED] In staging, 40 queries pass. These 3 fail with a syntax error. [report.md]
  • [INFERRED] During the rollback window, the same release must run on MySQL and on PostgreSQL. Q3 has one form that both accept. Q1 and Q2 do not. [report.md]

Why it matters

  • Q1 adds items to the cart. If Q1 fails, customers cannot buy.
  • Q2 feeds the nightly report.
  • Q3 pages the order search for the support team.

Proposed action

Rewrite the 3 queries. Use LIMIT 20 OFFSET 40 for Q3, because both databases accept it. Keep a per-database version of Q1 and Q2. The service selects the version at start-up. Effort: 2 days.

F3Report §3.3reviewMediumnot answered

Implicit type casts and zero dates break on PostgreSQL

Seven call sites compare text with numbers, and 18,516 rows hold the zero date. Bind the parameters as strings and convert each zero date to NULL during the copy.

Show details

The problem

MySQL converts types without a warning. PostgreSQL does not. Two patterns in the code and the data depend on the MySQL behaviour.

What we found

  • [READ] 7 call sites compare a VARCHAR column with a number. An example is WHERE order_number = ? with a long parameter. [report.md]
  • [TESTED] PostgreSQL rejects 5 of the 7 with operator does not exist: character varying = bigint. [report.md]
  • [UNVERIFIED] The staging tests do not reach the other 2 call sites. I expect the same error.
  • [TESTED] 18,204 rows in orders.shipped_at and 312 rows in returns.closed_at hold 0000-00-00 00:00:00. PostgreSQL does not accept this value. [report.md]
  • [READ] The service already reads the zero date as NULL (zeroDateTimeBehavior=convertToNull). [report.md]

Why it matters

A failed comparison returns an error page to the customer. A zero date stops the bulk copy of its table.

Proposed action

  1. Bind the 7 parameters as strings.
  2. Add a test for each of the 7 call sites.
  3. Set the copy tool to write NULL for each zero date.

Effort: 1.5 days. The service already reads the zero date as NULL, so its behaviour does not change.

F4Report §3.4reviewHighnot answered

Three DATETIME columns hold local time, and the other 31 hold UTC

MySQL triggers write local time into 3 columns, and the service writes UTC into the other 31. Convert all 34 columns to timestamptz, each read in its true time zone.

Show details

The problem

A MySQL DATETIME value has no time zone. The value means UTC or local time, depending on the code that wrote it. The copy to PostgreSQL must know which.

What we found

  • [READ] The service sets its clock to UTC. 31 of the 34 DATETIME columns get their values from the service. [report.md]
  • [READ] 3 columns get their values from MySQL triggers that call NOW(). The host runs on local time (UTC+1, with daylight saving). [report.md]
  • [TESTED] For the same order, order_events.created_at is 1 or 2 hours later than orders.created_at. [report.md]
  • [INFERRED] At each autumn clock change, one local hour occurs two times. About 38,000 rows fall in these hours. [report.md]

Why it matters

Reports that join these tables show times that are 1–2 hours wrong. If the copy reads all 34 columns as UTC, the error becomes permanent in PostgreSQL.

Proposed action

Convert all 34 columns to timestamptz. Read each column in its true time zone. Mark the ambiguous rows in a new column tz_ambiguous. In PostgreSQL, the triggers call now(), which returns a timestamptz. New rows are then correct. Effort: 3 days.

Recommendation

Option a. The move is the cheapest time to fix the data. After the move, each fix needs a new migration of a 288 GB table.
