Three DATETIME columns hold local time, and the other 31 hold UTC

MySQL triggers write local time into 3 columns, and the service writes UTC into the other 31. Convert all 34 columns to timestamptz, each read in its true time zone.

Show details

The problem

A MySQL DATETIME value has no time zone. The value means UTC or local time, depending on the code that wrote it. The copy to PostgreSQL must know which.

What we found

  • [READ] The service sets its clock to UTC. 31 of the 34 DATETIME columns get their values from the service. [report.md]
  • [READ] 3 columns get their values from MySQL triggers that call NOW(). The host runs on local time (UTC+1, with daylight saving). [report.md]
  • [TESTED] For the same order, order_events.created_at is 1 or 2 hours later than orders.created_at. [report.md]
  • [INFERRED] At each autumn clock change, one local hour occurs two times. About 38,000 rows fall in these hours. [report.md]

Why it matters

Reports that join these tables show times that are 1–2 hours wrong. If the copy reads all 34 columns as UTC, the error becomes permanent in PostgreSQL.

Proposed action

Convert all 34 columns to timestamptz. Read each column in its true time zone. Mark the ambiguous rows in a new column tz_ambiguous. In PostgreSQL, the triggers call now(), which returns a timestamptz. New rows are then correct. Effort: 3 days.
